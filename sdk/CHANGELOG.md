# Changelog — @decidio/sdk

Release notes for the client SDK. The Python package `decidio` ships under the same version; the core -
the gate, signing, receipts and the verifier - is conformance-locked between the two, while the command line's
first-run surfaces (the fork, `--demo`, the code sign-in) are TypeScript-first and named as such in the parity
allowlist. Each entry names what changed, what a reader must do on upgrade, and what proved it.

## Unreleased

## 0.21.0 - managed approvals and source-available SDKs (2026-11-20)

- **Recorded emergency approvals for managed Claude Code.** During a Decidio outage, an administrator can enable the
  emergency route on a locked computer. Interactive requests still require a local approval. Background requests stay
  held. When the computer reconnects, it files the emergency review for an Executive.
- **GitHub deploy setup uses decidio-actions v1.4.0.** New workflows generated by `github init` pin this version.
- **Coding-agent commands require a person.** Workspace policy can route a command to an approver. The approver still
  decides whether it can run.

- **A new licence: the Functional Source License (FSL-1.1-ALv2)**. From this release `@decidio/sdk`, the `decidio` command
  on npm and the `decidio` Python package are licensed under FSL-1.1-ALv2 instead of Apache-2.0. You may use, change and
  redistribute them for anything except a product or service that competes with Decidio, and each version also becomes
  available under Apache-2.0 two years after its release. `@decidio/verify` stays Apache-2.0, so anyone can check a receipt.
  0.20.1 and earlier stay Apache-2.0. Nothing to change in your code.
- **`dist/cli.d.ts` no longer ships**. The command line's type declarations were never importable (the package's exports map
  has no entry for them), so nothing that builds against the SDK changes. The `decidio` command is unchanged.
- **`@decidio/verify`: `verifyBoundRequest` checks the request an agent receipt was sealed for, offline**. An agent receipt sealed
  by Decidio now carries `authority.boundRequest`: a hash of the agent's own request commitment and, for a coding-agent command that
  went to a person, Decidio's digest of what its gate received. `verifyBoundRequest(vc, { request, commitmentKey?, gateKey? }, issuer?)`
  verifies the receipt, checks the disclosed request's amount (within half a cent, looser above about 5.6×10^12), action and scope against what the receipt seals in the
  clear (the action and scope byte for byte; one that holds a masked name doesn't verify offline yet), then rebuilds every sealed
  digest under its key. It returns the receipt's issuer and requester (whose DID counts only when `identityVerified` is true). The arguments and the context rest on the agent's commitment alone (Decidio shows the context to the approver but seals no
  digest of it, beyond a coding-agent card's seven committed details). The README gives both key derivations.
  TypeScript only. **On upgrade:** nothing to do; receipts sealed before carry no bound request and are reported as such.
- **The hook sees through links and hard links**. A path is followed through the
  links on the way - the file's own included, and a link whose target isn't made yet - and a file with a second name is compared by
  identity (device and inode) with the settings files in your and the project's `.claude`, so a shell write through a link to Claude
  Code's settings or the Decidio plugin's files, or through a hard link to those settings, is asked about as `decidio-guard`, with
  the real file on the card. Claude's Write and Edit tools get the same check whenever Claude
  Code starts the hook for them - by the path's spelling, so a hard link never matches and a link is unmeasured. `ln`, `link`, `cp -l`/`cp -s` and `mklink` over a
  protected file, or making a second name for one, are asked about. A recursive delete through a linked folder names where it leads
  and binds the real place (a re-pointed link is a new request). A card field cut to its limit ends "… (+N characters)". **On
  upgrade:** nothing to do; a path that is plainly itself reads and binds as before. Proved by `cli-smoke.ts` (five checks).
- **`hook lock --strict` holds Claude's file tools too, and fails closed without its sandbox**.
  The strict lock now adds Read deny rules for the credential folders it already hides from shell commands (Claude Code's sandbox
  holds shell commands only), and sets the sandbox's `failIfUnavailable`: on Linux without bubblewrap and socat, on WSL1 (or on Ubuntu while
  AppArmor's restriction on user namespaces stops bubblewrap, until it has the profile Claude Code's sandboxing page gives), Claude
  Code refuses to start instead of running unsandboxed. **Upgrade:** run `hook lock --strict` again on locked computers to pick it
  up; a computer whose sandbox never started (Claude Code said nothing) then won't start Claude Code until it has one. A strict
  lock's "Updates:" line and the `--print` it names now keep `--strict` (they printed the plain command). The pause's reply also
  names the teammate approver who confirms it.

- **Requests nobody answers: a typed `unanswered` outcome**. An agent's request a person must approve now has a deadline: seven days from when it was asked (no grace). If
  nobody decides it by then, Decidio closes it and no authority is granted. `/agent/status` still answers `state: "rejected"` - so
  an older SDK stops rather than waits - and adds the typed `closedBy: { reason: "unanswered", deadline }` (`reason` stays the
  person's own words, so it is null here). This SDK reads it: the blocking wait, `checkApproval` (new code `unanswered`, with
  `deadline`) and `approvalRefusal` throw the new **`DecidioUnansweredError`** (`code: "unanswered"`, `decisionId`, `deadline`) - it
  is NOT `DecidioRejectedError` (nobody refused it) and not `expired` (that is an approval that lapsed before it ran). The durable
  resume discards the parked action as final with the new outcome status `unanswered`. The coding-agent hook and `hook wait` say
  "closed unanswered" - never "the person refused it" - and a retry of the same change asks again (Decidio closes the old request
  and makes a new one). A `/agent/confirm` refused for such a request names it in its note. New exports: `DecidioUnansweredError`,
  `unansweredOf`, `UNANSWERED_WORDS`. **On upgrade:** code that catches `DecidioRejectedError` to mean "a person said no" no longer
  sees unanswered requests there - catch `DecidioUnansweredError` to ask again. Proved by `smoke.ts` (three checks, mirrored in
  `smoke.py`) and `cli-smoke.ts` (the hook and `hook wait`).

## 0.20.1 - the Python package reaches PyPI (2026-11-18)

- **No code change from 0.20.0.** 0.20.0 published to npm with provenance, but its PyPI upload was refused by the upload action's
  older twine (Metadata-Version 2.5), so PyPI went from 0.19.0 straight to 0.20.1. The public workflow now uses
  `pypa/gh-action-pypi-publish` v1.14.3 and checks the Python build with the same twine before anything is published. The Claude plugin (`decidio-approvals` 0.15.1) runs 0.20.1.

## 0.20.0 - published with provenance, and the hook guards Monitor and MCP calls (2026-11-17)

- **Published from a public repository, with provenance.**
  - From this release, `@decidio/sdk`, `@decidio/verify` and `decidio` are built and published by
    [`OmniTwin/decidio-sdk`](https://github.com/OmniTwin/decidio-sdk) through npm trusted publishing. Each version carries a
    provenance statement naming the commit and workflow run that built it, and `npm audit signatures` checks it.
  - The Python package carries PyPI attestations.
  - **Upgrade:** none. The package's code and contents are unchanged by this.
- **The Claude plugin and cloud sessions run 0.20.0.** The `decidio-approvals` plugin (0.15.0) and the hook set Decidio's
  connector writes for a cloud session (`enable_guard`) pin this release. That set now matches the plugin's: it also gates Monitor
  and the MCP tool calls the hook reads, and shows the one-time notice after other MCP calls.
- **The hook reads inside task runners**. `make`, `just` and `npm`/`pnpm`/`yarn`/`bun` scripts (pre/post scripts, the install lifecycle, the common workspace
  selectors, arguments after the script name) are read up to three files deep, and each line is checked by the same rules as a typed
  command: a force push in a `predeploy` script, or `make deploy`, now asks. **Changed:** a delete of plain build output inside the
  project (`dist`, `build`, `node_modules` and the like) in a script the hook follows no longer asks - `npm run build` with
  `rm -rf dist && tsc` asked before and is quiet now; typing `rm -rf dist` still asks. It is quiet only in a script that doesn't
  change folder or run other code first: a recipe that does `cd web && rm -rf dist`, or a typed `cd web && npm run build`, asks (use
  `npm run build -w web`).
- **`github lockdown`: lock a deploy down for you**. Run by the
  workspace owner in the bound repository's checkout, it signs in through GitHub's own CLI (`gh auth login --web`; Decidio never
  sees the token), reads Decidio's lock-down check, and plans the three settings - the Actions policy on the deploy workflow,
  production's branches with the admins-only rollback rule, and a "reviewed changes" ruleset that nobody bypasses (or none, with
  `--without-review-rule`) with CODEOWNERS lines written to the checkout. It applies only on a yes (`--yes --plan <id>` from a dry
  run), then reports to Decidio what GitHub shows. **Applying is off by default for now:** it needs `DECIDIO_GITHUB_LOCKDOWN_APPLY=1` until it has been proven on a real
  repository; the dry run and the plan work without it.

- **The coding-agent hook trusts only Decidio's signed answers**. A policy's yes, a person's approval and a pause let a command through only when Decidio signed that answer
  for this request, this Claude Code session and this run (a fresh challenge each run), checked against the issuer built into this
  SDK for the host it asks - never one the `.env`, settings or the server names. A host with no built-in issuer (a stand-in on
  this computer, a look-alike, localhost) is refused before anything is asked. A person's approval is claimed - spent - before the
  `allow`, so the same approval can't run twice. **Upgrade:** none for hosted Decidio. A self-hosted Decidio is refused by the hook until the lock pins its issuer
  (`hook lock`).
